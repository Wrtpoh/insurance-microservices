# Информационная система страховой компании: микросервисы (Python)

Четыре микросервиса и API-шлюз на FastAPI. У каждого сервиса своя база данных (SQLite для разработки,
замена на PostgreSQL — сменой `DATABASE_URL`), общих таблиц нет, сервисы общаются только по HTTP.

```
Клиент ──► API Gateway :8000 ─┬─► Client Service  :8001  (clients)
                              ├─► Product Service :8002  (products)
                              ├─► Policy Service  :8003  (policies, transactions) ──► Client, Product
                              └─► Claim Service   :8004  (claims, payouts)        ──► Policy
```

## Запуск

```
pip install -r requirements.txt
python run_all.py            # все сервисы и шлюз; документация OpenAPI: http://127.0.0.1:800X/docs
python -m pytest             # 48 тестов
```

Через Docker (файлы подготовлены, но на машине разработки Docker не запускался):
`copy .env.example .env`, задать `JWT_SECRET`, затем `docker compose up --build`. Наружу открыт только шлюз :8000.

## Авторизация и роли

Вход: `POST http://127.0.0.1:8000/auth/login` с `{"username": "...", "password": "..."}` возвращает JWT;
дальше заголовок `Authorization: Bearer <токен>` для всех запросов `/api/...` (в Swagger шлюза: `/docs`).
Шлюз проверяет токен и права роли, передаёт сервисам `X-User` и `X-Role`, пишет изменяющие запросы в журнал.

| Логин (пароль для разработки) | Роль |
|---|---|
| `admin` (`admin123`) | Администратор |
| `manager` (`manager123`) | Руководитель |
| `agent` (`agent123`) | Страховой агент |
| `adjuster` (`adjuster123`) | Специалист по убыткам |

Пароли первого запуска задаются переменными `SEED_PASSWORD_<ЛОГИН>`, секрет токенов — `JWT_SECRET`.
Права соответствуют таблице «Роли и их полномочия» проектного решения (`gateway/permissions.py`):
администратор ведёт справочники, продукты и учётные записи (`/auth/users`); агент оформляет договоры, регистрирует
платежи и случаи; специалист по убыткам рассматривает случаи и создаёт выплаты; руководитель согласовывает
выплаты, подтверждает факт выплаты и оплату, отменяет договоры. Журнал действий: `GET /api/audit` (только администратор).

Примечание: сервисы доверяют шлюзу и должны быть доступны только из внутренней сети (в Docker Compose так и есть).

Сквозной сценарий: клиент → договор (`/api/policies`) → платёж и подтверждение
(`/api/policies/{id}/payments`, `/api/payments/{id}/confirm`) → страховой случай (`/api/claims`) →
рассмотрение (`/review`, `/approve`) → выплата (`/api/payouts`, `/approve`, `/execute`).

## Сервисы и API (по архитектурному плану)

| Сервис | Основные эндпоинты |
|---|---|
| Client Service | `POST /clients`, `GET /clients?q=`, `GET/PUT /clients/{id}` |
| Product Service | `GET /products?insurance_type=&status=`, `GET/PUT /products/{id}`, `POST /products` |
| Policy Service | `POST /policies`, `GET /policies/{id}`, `POST /policies/{id}/activate\|renew\|cancel`, `GET /policies/{id}/coverage`, `POST/GET /policies/{id}/payments`, `POST /payments/{id}/confirm` |
| Claim Service | `POST /claims`, `GET/PUT /claims/{id}`, `POST /claims/{id}/review\|approve\|reject\|close`, `POST /payouts`, `GET /payouts/{id}`, `POST /payouts/{id}/approve\|execute` |

Бизнес-правила (сервисы не сводятся к CRUD): уникальность телефона клиента; оформление договора проверяет
клиента и активность продукта, считает премию; платёж не может превысить остаток премии; договор активируется
только после полной оплаты; страховой случай регистрируется, только если договор оплачен и действовал на
дату события; выплата возможна только по одобренному случаю, одна на случай, не больше страховой суммы.

## Паттерны проектирования (GoF) в сервисах

| Тип | Паттерн | Где | Задача |
|---|---|---|---|
| Порождающий | Factory Method | `policy_service/factory.py` | договоры AUTO / HEALTH / PROPERTY со своим сроком и минимальной суммой |
| Порождающий | Builder | `claim_service/builder.py` | заявление о страховом случае: обязательные и необязательные поля, проверки |
| Структурный | Adapter | `policy_service/payment_gateway.py` | внешний банк (копейки, числовые коды) → `PaymentGateway` со статусами транзакций |
| Структурный | Decorator | `policy_service/premium.py` | премия = тариф + скидки/надбавки цепочкой |
| Структурный | Facade | `policy_service/facade.py` | оформление договора одним вызовом (клиент, продукт, фабрика, расчёт, сохранение) |
| Поведенческий | State | `claim_service/state.py` | статусы страхового случая и допустимые переходы |
| Поведенческий | Strategy | `claim_service/strategy.py` | правила расчёта выплаты: полная, франшиза, пропорциональная |
| Поведенческий | Observer | `policy_service/events.py` | после подтверждения платежа: is_paid, активация договора, журнал |

## Микросервисные паттерны (лекция «Микросервисная архитектура»)

| Паттерн | Реализация |
|---|---|
| Database per Service | своя БД у каждого сервиса, обращение к чужим данным только через API |
| API Gateway | `gateway/main.py`: единая точка входа `/api/<ресурс>`, маршрутизация по сервисам |
| Circuit Breaker | `common/resilience.py`: после 3 сбоёв вызов сервиса блокируется на 10 с, ответ 503 |
| Health Check | `GET /health` у каждого сервиса, агрегированный `GET /health` на шлюзе |
| Распределённая трассировка (упрощённо) | сквозной `X-Request-ID` через шлюз и межсервисные вызовы |
| Предметная связанность | Policy → Client/Product, Claim → Policy (по HTTP, без доступа к чужим БД) |

## Что уже сделано и что осталось

Сделано (примерно 45–50% проекта): все четыре бизнес-сервиса с БД и основными сценариями, шлюз,
межсервисное взаимодействие, устойчивость к отказам, 8 паттернов, аутентификация (JWT), роли и права по
матрице проектного решения, журнал действий, Docker Compose, 48 автотестов (юнит и сквозные через шлюз).

Осталось: отчёты с выгрузкой в Excel (4 отчёта из проектного решения), загрузка документов по страховым случаям,
веб-интерфейс, PostgreSQL вместо SQLite, миграции БД (Alembic), срок хранения логов и интеграции из проектного решения.
